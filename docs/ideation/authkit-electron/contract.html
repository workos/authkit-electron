The problem

01WorkOS AuthKit has no Electron SDK. Integrating it today means hand-wiring the full OAuth and session lifecycle across Electron's three isolated process contexts — main, preload, and renderer — as the electron-authkit-example repo does across src/main/auth/ (auth.ts, deep-link-handler.ts, ipc-handlers.ts), src/preload/index.ts, and the renderer's src/renderer/src/hooks/useAuth.ts.

02That hand-wiring concentrates several error-prone, security-sensitive concerns in application code: PKCE generation and expiry, authorization-code exchange, JWT-exp parsing and token refresh, the cross-platform custom-protocol deep-link capture matrix (open-url on macOS, second-instance on Windows/Linux, the dev-mode argv branch), safeStorage-backed persistence behind a hardcoded key, and a private IPC contract whose channel names are duplicated between preload and main behind a fragile 'must match' comment. The renderer additionally redefines its own User type (useAuth.ts), which drifts from @workos-inc/node's.

03Every team adopting AuthKit on Electron re-derives this same boilerplate and inherits the same latent bugs. WorkOS already ships @workos/authkit-session — the framework-agnostic core powering @workos/authkit-tanstack-react-start — whose AuthKitCore and AuthOperations are cookie-free and accept an injected WorkOS client, so the building blocks exist; there is simply no packaging of them for Electron's runtime model.

Goals ×7
01 Collapse the three-context integration to one call per context — createAuthKit() in main, exposeAuthKit() in preload, <AuthKitProvider> in the renderer — replacing the roughly five hand-wired files in electron-authkit-example.
02 Reuse @workos/authkit-session's core (AuthKitCore, AuthOperations, sessionEncryption) for all security-sensitive logic — zero re-implemented crypto, PKCE, JWT verification, or token-refresh code — operating as a PUBLIC OAuth client: construct the WorkOS client with clientId only (no API key shipped) and inject it into the core, bypassing the API-key-requiring getWorkOS() factory and the global ConfigurationProvider.
03 Confine the refresh token to the main process so it appears in no renderer-facing IPC payload, while exposing the short-lived access token through getAccessToken().
04 Persist the session at rest via safeStorage (OS keychain), and seal the in-flight PKCE verifier with a per-install, >=32-char cookiePassword generated on first run and stored in the keychain — no static secret ships in the binary (an upgrade over the example's hardcoded key).
05 Own the IPC contract inside the package so consumers never redeclare channel names, and surface @workos-inc/node's User and claims types directly to eliminate type drift.
06 Support both sign-in ceremonies — system-browser (default) and in-app window — and the full cross-platform deep-link capture matrix out of the box.
07 Ship as a single ESM package with subpath exports (root for main, /preload, /react) that version in lockstep, plus an in-repo example app that consumes it.

MVP — must ship ×8
  • Public-client config: createAuthKit({ clientId, redirectUri, cookiePassword }) constructs createWorkOS({ clientId }) (no API key) and injects it into authkit-session's AuthKitCore/AuthOperations— Desktop apps are public OAuth clients; shipping a WorkOS API key in a distributed binary would leak a confidential server credential. Bypasses the core's API-key-requiring getWorkOS() factory.
  • Main-process session manager on the injected core: getUser/getAccessToken/refresh (validateAndRefresh) + cleanup(), with multi-window broadcast of auth changes— The core 'server' half — nothing works without it; reuses the core's refresh dedup + rate-limit retry
  • Cross-platform deep-link capture: registerProtocol() + the open-url / second-instance / dev-argv matrix— The most error-prone hand-wired piece and the backbone of callback capture
  • system-browser ceremony mode (default): createAuthorization -> persist sealedState main-side -> shell.openExternal; callback re-orchestrated outside AuthService (verifyCallbackState -> authenticateWithCode)— Most secure, the recommended default; required for a usable MVP. AuthService.handleCallback is cookie-bound and cannot be reused.
  • preload exposeAuthKit() bridge with SDK-owned channel names— Removes the channel-duplication footgun between preload and main
  • /react: AuthKitProvider + useAuth() + useAccessToken()— The renderer surface applications consume
  • safeStorage-backed session persistence (refresh token confined to main) + per-install >=32-char cookiePassword in the keychain for sealing the in-flight PKCE verifier— Secure-by-default at-rest storage with no static secret shipped in the binary
  • User/claims types surfaced from @workos-inc/node— Eliminates renderer User-type drift
Full — target outcome ×5
  • window ceremony mode (in-app BrowserWindow) with navigation-intercept callback capture— Second sign-in mode for apps that prefer staying in-app
  • Guard components <SignedIn> / <SignedOut>— Convenience matching @clerk/clerk-react's declarative guards. (The AuthKit family ships an ensureSignedIn route-guard instead, which doesn't map to a router-less Electron renderer.) Explicitly requested.
  • switchToOrganization() via AuthOperations— Common multi-tenant requirement
  • In-repo example/ app evolved from electron-authkit-example— Living reference and the e2e target
  • Automated Playwright + Electron e2e covering both ceremony modes— Real-sign-in fidelity per the chosen test strategy
Stretch — if time permits ×2
  • Pluggable Electron storage adapter interface (swap electron-store for keytar or a custom backend)— Distinct from authkit-session's SessionStorage seam, which is cookie/HTTP-shaped and deliberately not used here — this is an Electron-native key-value seam
  • @workos/emulate as the deterministic e2e backend
Out of scope — said no on purpose
  • Native passkeys / WebAuthn module — AuthKit handles passkeys on its hosted page at a real https origin in both ceremony modes; no native module is needed (verified against WorkOS docs)
  • Non-React renderer bindings (vanilla, Vue, Svelte) — main and preload are framework-agnostic, so bindings can follow later with no rework
  • CJS output (dual ESM+CJS build) — authkit-session and the sibling SDKs are ESM-only; modern Electron supports ESM and the example bundles via electron-vite. CJS would require bundling an ESM-only dependency. Revisit only if a consumer needs a CJS main with no bundler.
  • Admin Portal, Directory Sync, and org-management UI — Not session/authentication concerns
  • Auto-update, packaging, and code-signing helpers — General Electron concerns outside authentication
Future — someday, maybe
  • Vanilla and Vue/Svelte renderer bindings
  • @workos/emulate-backed deterministic e2e
  • Dual ESM+CJS output if a consumer needs it
  • Documented window-mode Touch ID setup (Electron >= 42 + app.configureWebAuthn)

## Phase Kind Risk Notes
01 Core session engine phase · blocking med Public-client setup: construct the WorkOS client via createWorkOS({ clientId }) (no API key) and build an AuthKitConfig object directly (clientId, redirectUri, cookiePassword; apiKey set to '' since the injected client is what is used), bypassing authkit-session's getWorkOS() and ConfigurationProvider. Integrate AuthKitCore + AuthOperations + sessionEncryption; session manager (getUser/getAccessToken/refresh/signOut/switchToOrganization); safeStorage persistence; per-install keychain cookiePassword. Pin @workos-inc/node peer to a range matching authkit-session (^10.x, aligned with the newest sibling tanstack-start; the example must bump off 8.0.0-rc.10). Unit-tested against a mocked WorkOS client; no Electron windows yet.
02 Ceremony, deep-link & IPC phase · blocking high system-browser sign-in via AuthOperations.createAuthorization (returns { url, sealedState }; the auth URL carries state=sealedState). RE-ORCHESTRATE the callback outside AuthService (AuthService.handleCallback is cookie/SessionStorage-bound and unusable): persist the sealedState verifier main-side in electron-store (not a cookie), then at callback feed the deep-link state param to AuthKitCore.verifyCallbackState as cookieValue, unseal, call client.userManagement.authenticateWithCode({ code, clientId, codeVerifier }), build the Session, persist via safeStorage, and single-use-delete the verifier. Cross-platform deep-link capture (registerProtocol + open-url/second-instance/argv). IPC handlers with discriminated-union results + multi-window broadcast; preload exposeAuthKit bridge.
03 React bindings phase · blocking low @workos/authkit-electron/react: AuthKitProvider, useAuth, useAccessToken, <SignedIn>/<SignedOut>. Consumes the SDK-owned IPC bridge; the renderer never sees the refresh token. Surfaces @workos-inc/node User/claims types.
04 In-app window ceremony mode phase · blocking med ceremony.mode 'window': child BrowserWindow to the hosted AuthKit page, navigation-intercept callback capture, preventDefault before the protocol handler fires to avoid a double-handle. Reuses the Phase 2 callback re-orchestration.
05 Example app + automated e2e phase med Seed example/ from electron-authkit-example consuming the published SDK API (resolving the package from built dist); Playwright + Electron e2e with a passing sign-in test for EACH ceremony mode; wire lint/format/export-resolution into CI.
